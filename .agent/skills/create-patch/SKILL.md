---
name: create-patch
description: Roll up in-place edits made via vendor-module into one or more new, immutable Bazel module versions ready to commit as a PR. Use this once you've fixed and tested a package's vendored source and are ready to turn it into a mergeable change; also use it if you're not sure which vendored packages you actually touched.
---

`//tools/ci:create_patch` diffs your vendored edits against **raw** upstream
(not the currently-published version — every `.rcr.N` patch describes a
transformation relative to the same original archive, not an incremental
delta), and writes the result as a brand-new module version directory, e.g.
`rclcpp@32.0.0-1.rcr.1` -> `rclcpp@32.0.0-1.rcr.2`.

Requires a workspace already generated by `setup-workspace`, with at least
one package vendored and edited via `vendor-module`.

## Fixing one specific package

```shell
# from the repo root, not inside workspace/
bazel run //tools/ci:create_patch -- rclcpp
```

This is deterministic and non-interactive: it either creates exactly one new
`modules/rclcpp/<new-version>/` directory, or prints "No changes detected"
and does nothing.

## Not sure which vendored packages you actually edited?

Omit the module name. This is the right choice whenever you've vendored
several packages (or a whole `--variant`/`--all`) and only touched some of
them:

```shell
bazel run //tools/ci:create_patch --   # no module argument
```

This auto-detects every vendored module with real local edits (cheaply,
via the file-hash manifest `vendor-module` records — no network fetch for
packages you didn't touch), prints a summary per changed package, then asks
for one confirmation before rolling all of them up:

```
Detected changes in 2 vendored module(s):
Creating rclcpp@32.0.0-1.rcr.2 (from 32.0.0-1.rcr.1):
  patches: 1 (was 0)
  overlay: 0 (was 0)
Creating rclcpp_action@10.2.1-2.rcr.1 (from 10.2.1-2):
  patches: 0 (was 0)
  overlay: 1 (was 0)
Roll up 2 module(s) into new patch versions? [y/N]:
```

Useful flags in this mode:

- `--yes` / `-y` — skip the confirmation (e.g. running non-interactively).
- `--dry-run` — print what would happen (works in both modes) without
  writing or prompting.

## What your PR should look like

Exactly the new version directory/directories under `modules/<package>/`,
plus the corresponding `metadata.json` updates (a new entry appended to
`versions`) — nothing else. **Never** touch an existing version directory or
any other package's files: `tools/ci/check_pr_modules.py` enforces this in
CI and will fail the PR otherwise (see the immutability rule in
`AGENTS.md`).

When you open the PR, fill out every section of
`.github/PULL_REQUEST_TEMPLATE.md` (GitHub applies it to the description
automatically) — in particular:

- **Packages affected** — name the package(s) you just rolled up.
- **Generative AI disclosure** — if you are the agent that produced this
  patch (or materially assisted with it), disclose that honestly per the
  linked OSRF Generative AI policy; don't leave it blank or answer "No" on
  its behalf.
- **Related issue** — link the issue this patch fixes, if any.

## Gotchas

- "This workspace resolved X to A, but the latest published version is B" —
  the workspace is stale (someone else's patch to that package merged since
  you set up the workspace). Re-run the `setup-workspace` skill, then
  `vendor-module` again, before creating the patch — don't hand-adjust
  version numbers.
- "does not exist. Run 'bazel run //tools/ci:vendor_modules -- <module>'
  first" — you haven't vendored that package in this workspace yet; go back
  to the `vendor-module` skill.
- If auto-detect mode finds nothing, either nothing was actually edited, or
  the edits exactly match what's already published — both are reported and
  are not errors.
