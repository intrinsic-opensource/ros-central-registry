`//tools/ci:vendor_modules` materializes one or more packages' actual source
trees (patches/overlay already applied) under `workspace/vendor/<name>+/`, so
you can edit them in place and immediately rebuild/retest with Bazel — Bazel's
`--vendor_dir` support means builds transparently pick up your edits without
any repo-relative symlink dance.

Requires a workspace already generated by the `setup-workspace` skill.

## Basic usage

```shell
cd workspace   # the directory setup_workspace generated

bazel run //tools/ci:vendor_modules -- rclcpp
```

This fetches `rclcpp`'s real source into `workspace/vendor/rclcpp+/`.

## Vendoring more than one package

Multiple modules in one command — either form works:

```shell
bazel run //tools/ci:vendor_modules -- rclcpp rclcpp_action rclcpp_lifecycle
bazel run //tools/ci:vendor_modules -- "rclcpp rclcpp_action rclcpp_lifecycle"
```

A canned ROS variant (uses the package-name spelling — see the
`setup-workspace` skill's note on the two variant-naming conventions):

```shell
bazel run //tools/ci:vendor_modules -- --variant ros_core
bazel run //tools/ci:vendor_modules -- --variant ros_base desktop_full
```

Every declared module in the workspace:

```shell
bazel run //tools/ci:vendor_modules -- --all
```

`--all` can't be combined with explicit modules or `--variant`; explicit
modules and `--variant` can be combined with each other.

## Editing and testing

```shell
# still inside workspace/
$EDITOR vendor/rclcpp+/src/some_file.cpp
bazel test @rclcpp//...
```

Only test the package(s) you're actually changing — don't build/test the
whole variant unless you have a specific reason to (it's slow, and CI already
runs the full matrix on your PR).

## Once you're happy with the fix

Move on to the `create-patch` skill to turn your edits into a new module
version — that's your actual deliverable, not the `vendor/` tree itself
(which is gitignored and never committed).

## Gotchas

- `vendor/<name>+/MODULE.bazel` is never diffed by `create-patch` — don't
  bother editing it.
- Re-vendoring a package you've already vendored resets the local-edit
  baseline that `create-patch`'s auto-detect mode compares against (it
  snapshots a file-hash manifest into `workspace/.vendor_manifest/` right
  after every vendor run). Don't re-run `vendor_modules` on a package
  mid-edit unless you mean to reset that baseline.
- If a package isn't declared as a `bazel_dep` in the workspace's
  `MODULE.bazel`, vendoring it fails loudly rather than silently no-op-ing —
  that usually means you need to re-run `setup-workspace` (wrong release) or
  the package genuinely isn't part of this release yet.
