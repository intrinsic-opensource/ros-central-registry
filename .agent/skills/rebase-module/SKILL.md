`//tools/ci:rebase_module` is the recovery path from `create-patch`'s
drift-detection refusal (see the `create-patch` skill's Gotchas) or from any
other "my workspace is stale but I have uncommitted edits worth keeping"
situation. It replaces the fully-manual "re-run `setup-workspace`, re-run
`vendor-module`, redo my edits by hand" dance — which silently discards
uncommitted work (see `AGENTS.md`) — with one command.

Requires a workspace already generated by `setup-workspace`, with the
module(s) you're rebasing vendored via `vendor-module`.

## Basic usage

Run from the repo root, same as `create-patch`:

```shell
bazel run //tools/ci:rebase_module -- rosdistro
```

This:

1. Captures your current edits to `workspace/vendor/rosdistro+/` relative to
   the last `vendor-module` snapshot (`workspace/.vendor_snapshot/`).
2. Re-runs `setup-workspace` and `vendor-module` to get a fresh baseline
   from whatever's currently on disk under `modules/`.
3. Reapplies your captured edits on top of that fresh baseline.

Multiple modules in one command works the same way `vendor-module` does
(space- or comma-separated):

```shell
bazel run //tools/ci:rebase_module -- rclcpp rclcpp_action
```

Useful flags:

- `--release NAME` — re-baseline against a specific release instead of
  whatever `workspace/MODULE.bazel` already pins.
- `--dry-run` — print what would be captured/reapplied without touching the
  workspace.

## Reading the output

A clean rebase looks like:

```
rosdistro:
  patches applied cleanly: 2
  overlays written: 1
Done. Resolve any conflicts above ..., then re-test and re-run //tools/ci:create_patch.
```

If a patch can't be cleanly reapplied onto the fresh baseline (because the
concurrent change it collided with touched the same lines), you'll see:

```
  patches with CONFLICTS (.rej files written): src__c.patch
```

Find the `.rej` file next to the target under `workspace/vendor/<module>+/`
and resolve it by hand — same workflow as resolving a `git`/`patch` reject
file anywhere else: look at what the fresh baseline has, what your edit was
trying to do, and reconcile them manually in the actual source file.
**Always delete the `.rej` file after resolving the conflict**, so `create_patch`
does not capture it as a new overlay file.

An overlay (brand-new file you added) that collides with a same-named file
the fresh baseline itself introduced is reported too, but your content is
still written — review it, since two people adding a same-named file
independently is worth a second look even though nothing failed outright.

## `MODULE.bazel` is never auto-merged

If you'd edited `rosdistro`'s `MODULE.bazel` (the one module allowed
free-form edits there — see the `create-patch` skill), your edited content
is **not** reapplied automatically. It's written aside to
`workspace/.rebase_conflicts/rosdistro.MODULE.bazel.your-edits` and flagged
in the output; reconcile it into the freshly-vendored `MODULE.bazel` by
hand. `MODULE.bazel` is executable and dense with near-identical
`bazel_dep(name=..., version=...)` lines, so a line/context-based patch is
far more likely to apply cleanly *while being semantically wrong*
(duplicate `bazel_dep`, a version landing in the wrong block) than to fail
loudly — a human needs to look at it. For any other module, a `MODULE.bazel`
hand-edit is simply dropped with a note (non-`rosdistro` packages are never
supposed to have real `MODULE.bazel` edits in the first place).

## Once you're happy with the rebased state

Ensure all `.rej` files are removed, re-test (`bazel test @<module>//...`), and continue with the `create-patch`
skill as usual.

## Gotchas

- Requires `workspace/.vendor_snapshot/<module>+/` to exist, which only
  workspaces vendored after this tool was added will have. If it's missing,
  re-run `vendor-module` (this does discard uncommitted edits — there's
  nothing to rebase from without the snapshot).
- The two nested `bazel run` calls (`setup-workspace`, `vendor-module`) are
  expected and normal — same pattern `vendor-module` itself uses internally
  for `bazel vendor`.
- Patch reapplication shells out to the system `patch` CLI (GNU patch, same
  as most Linux/macOS dev environments ship by default) — not a Python
  reimplementation.
